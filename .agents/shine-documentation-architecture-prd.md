# Shine 文档独立发布与公私内容分层 PRD

## 1. 文档状态

| 项目 | 内容 |
|---|---|
| 状态 | Draft |
| 适用仓库 | `shine`、`blog`、`blog-private` |
| 目标读者 | Shine 维护者、文档维护者、发布流程维护者、AI Agent |
| 主要产物 | Shine 公开文档站、Biulight 公共内容门户、Biulight 内部文档聚合站 |

本文定义 Shine 公开产品手册从 `blog` 迁入 `shine` 后的内容归属、发布方式、私有内容边界、
跨仓同步规则和迁移验收标准。本文是实施设计依据，不是当前系统已经完成的行为说明。

## 2. 摘要

Shine 已形成独立且高频更新的产品手册。继续把完整手册维护在 `blog` 中，会使产品代码和用户
文档分属两个提交与发布边界，依赖 `last_reviewed_ref` 才能确认是否同步。与此同时，
`blog-private` 需要同时呈现公共手册、公共知识和内部扩展，但其中的真实网络、ShineOverlay、
内部任务和运维信息不能进入公开仓库或公开 Pages 构建。

本 PRD 采用三仓分工：

1. `shine` 是 Shine 中英文公开产品手册的唯一权威来源，并从 `release` 分支发布公开站点；
2. `blog` 是 Biulight 公共门户、博客和跨产品通用知识的唯一权威来源；
3. `blog-private` 是内部原始内容的唯一权威来源，并在构建前聚合前两者的公开内容；
4. 任何一篇内容只能有一个可编辑的权威来源，生成副本不得人工修改；
5. 私有内容只允许从 `blog-private` 经人工脱敏改写后进入相应公开仓库，不允许机械反向同步。

目标不是简单移动 Markdown 文件，而是建立能长期保持产品事实、公私边界和发布版本一致的文档
架构。

## 3. 背景与问题

### 3.1 产品手册与代码发布不同步

当前公开 Shine 手册位于 `blog/docs/products/shine/`，产品实现位于 `shine`。产品仓库是命令、
配置、兼容性和发布版本的事实来源，但用户手册需要在另一个仓库单独更新、构建和发布。

现有 `.agents/projects.yml` 使用 `last_reviewed_ref` 记录已经审阅的 Shine revision。这能发现落后，
但不能保证功能实现、手册修改和版本发布在同一个 PR 中完成。快速迭代期间可能出现：

- 新版本已发布，公开手册仍描述上一版本；
- 代码评审无法同时看到对应的用户文档；
- 文档维护者需要跨仓还原命令与配置变化；
- README、中文 README 和完整手册重复维护相同契约。

### 3.2 公开手册与内部扩展存在不同安全边界

`blog-private` 目前承载以下内容：

- 真实内网域名、主机名、地址和拓扑；
- ShineOverlay 的内部使用方式和私有仓库引用；
- 内部任务、部署流程和故障实录；
- 可在脱敏改写后发布的内部实践原文；
- 公共 Shine 手册和公共知识的生成副本。

这些内容必须继续由访问控制保护。`noIndex`、隐藏导航、未公开 URL、单独分支或从 Pages 构建中
排除文件，都不能替代仓库和站点级访问控制。公开 Git 仓库中的历史提交同样视为公开。

### 3.3 公共知识不应被产品仓库吸收

YubiKey、ZeroTier、Split-DNS、代理原理等文章可能以 Shine 为实践工具，但其知识价值可以跨产品
复用。若为了手册独立而把这些内容全部迁入 `shine`，会导致通用知识被产品导航绑架，并增加
多个产品重复解释相同概念的风险。

### 3.4 内部站仍需要统一阅读体验

内部读者处理问题时经常需要在公开命令参考、通用知识和内部环境说明之间切换。完全取消公共
内容镜像会使内部文档产生大量跨站跳转，也会失去统一全文搜索。因此，内部站仍应在构建时聚合
公开内容，但不得改变其权威来源。

## 4. 产品目标

### 4.1 主要目标

- 让 Shine 功能、命令、配置与对应公开手册能够在同一个 PR 中修改和评审。
- 让稳定版公开手册明确对应 `shine/release` 的已发布行为。
- 同时提供英文和简体中文完整手册，以英文作为公共站默认语言。
- 为 Shine 提供独立、稳定且可迁移的公开文档入口。
- 保留 Biulight 公共门户、博客与跨产品知识库的统一定位。
- 保留内部站中“公共内容 + 内部扩展”的统一导航和搜索体验。
- 让每篇文档都能确定唯一权威来源、发布范围和同步方向。
- 让同步结果可追溯到准确的源 commit，并能检测生成副本被人工修改。
- 在迁移过程中保持现有公开 URL 可达，避免已有链接和搜索索引突然失效。

### 4.2 成功结果

迁移完成后：

1. 修改 Shine 用户可见行为的 PR 可以同时修改对应手册；
2. `shine` 的 `release` 分支构建并发布稳定公开手册；
3. `blog` 不再保存可编辑的 Shine 完整手册，只保留产品入口和旧 URL 跳转；
4. `blog-private` 从 `shine` 和 `blog` 两个来源生成公共内容副本，同时保留自己的内部内容；
5. 内部内容不会出现在任何公开仓库历史、公开构建产物、公开搜索索引或站点地图中；
6. 英文手册使用站点根路径，简体中文手册使用独立 locale 路径，页面范围保持一致；
7. 内部原文的公开衍生版本能明确路由到 `shine` 或 `blog`，且必须经过人工脱敏审阅。

## 5. 非目标

- 不把 Shine 的 ADR、PRD、架构知识库和发布 Runbook 公开为用户手册。
- 不把 `blog-private` 迁入 `shine`，也不在公开仓库中建立所谓“隐藏私有目录”。
- 不在 v1 建立多版本文档站；稳定站只对应当前已发布版本。
- 不把“默认英文”解释为只维护英文；英文和简体中文都属于稳定版发布要求。
- 不自动把内部文章通过字符串替换或字段删除转换成公开文章。
- 不要求公共站与内部站使用完全相同的主题、搜索实现或部署平台。
- 不在本次迁移中重新设计全部 Biulight 品牌、博客信息架构或所有产品文档。
- 不把真实凭据提交到私有仓库；私有仓库仍不得保存密码、Token、私钥、Cookie 或恢复码。
- 不以 GitHub Pages 作为永久不可替换的架构依赖；Pages 只是首选托管实现。

## 6. 用户与核心场景

### 6.1 Shine 用户

- 从 Shine README、GitHub About 或 Release 页面进入与稳定版本一致的完整手册。
- 默认进入英文手册，并能通过始终可见的语言切换入口访问简体中文手册。
- 使用稳定 URL 查找安装、快速开始、任务指南、命令、配置和排错信息。
- 从产品手册跳转到 Biulight 公共知识库阅读通用背景知识。

### 6.2 Shine 维护者

- 在实现用户可见变更时同步修改手册，并在同一个 CI 中发现命令、链接或构建错误。
- 发布 `release` 分支时自动发布对应的稳定文档。
- 不再维护 README 中与完整手册重复的大段参考内容。

### 6.3 内部读者

- 在受访问控制保护的内部站中搜索公共手册、公共知识和内部扩展。
- 从公开命令说明继续进入真实内部环境的操作步骤，而不需要在多个站点反复定位。
- 能清楚识别页面是公共镜像还是内部专属内容。

### 6.4 文档维护者和 AI Agent

- 根据页面类型确定权威仓库，不创建循环同步。
- 通过源 revision 判断内部聚合站中的公共副本是否过期。
- 在发布脱敏版本时，明确目标仓库并执行人工安全审查。

## 7. 内容归属模型

### 7.1 三个权威来源

| 内容类型 | 权威仓库 | 建议路径 | 是否公开 |
|---|---|---|---|
| Shine 英文安装、快速开始、命令、配置、排错 | `shine` | `docs/manual/` | 是 |
| Shine 英文专属任务指南 | `shine` | `docs/manual/guides/` | 是 |
| Shine 简体中文手册 | `shine` | 站点的 `zh-Hans` locale 内容根 | 是 |
| Shine 内部 ADR、架构、经验、PRD | `shine` | 现有 `docs/kb/`、`docs/*-prd.md` | 否，不进入公开构建 |
| Biulight 产品入口 | `blog` | `docs/products/` | 是 |
| 跨产品通用知识 | `blog` | `docs/knowledge/` | 是 |
| 公共博客文章 | `blog` | `blog/` | 是 |
| 内部通用指南 | `blog-private` | `docs/internal/` | 否 |
| ShineOverlay 与环境扩展 | `blog-private` | `docs/products/shine/internal/` | 否 |
| 内部公告、复盘、周报等时间流文章 | `blog-private` | `blog/internal/` | 否 |
| 公共内容在内部站中的副本 | 其原公开仓库 | `blog-private` 中的生成目录 | 仅内部站展示，不可编辑 |

### 7.2 分类决策

新增或修改内容时按顺序判断：

1. 是否包含真实内部环境、私有仓库、内部任务、拓扑或不能公开的标识？
   - 是：权威来源为 `blog-private`。
2. 是否描述 Shine 独有的公开行为、命令、配置、兼容性或排错？
   - 是：权威来源为 `shine`。
3. 是否脱离 Shine 后仍能作为网络、安全、硬件、开发或运维知识独立成立？
   - 是：权威来源为 `blog`。
4. 是否只是另一个权威来源的构建副本？
   - 是：禁止人工编辑，必须修改源文件后重新同步。

### 7.3 唯一权威来源原则

同一篇完整内容不得同时在两个仓库中人工维护。允许以下关系：

- 权威源文件 → 自动生成副本；
- 内部完整原文 → 人工改写的脱敏公开版本；
- 旧公开 URL → 跳转或迁移提示页；
- 公共产品指南 → 指向公共通用知识的链接。

以下关系不允许：

- 两个仓库各自修改同一篇公共手册；
- 生成副本反向覆盖权威源文件；
- 脱敏公开版本反向覆盖内部完整原文；
- 使用双向同步工具自动解决内容冲突；
- 在 README、中文 README 和任一语言站点手册中重复维护完整命令参考。
- 只更新一个语言版本后发布稳定站，造成两个 locale 描述不同产品行为。

## 8. 目标架构

### 8.1 内容流

```text
shine/docs/manual/ ───────────────────────┐
                                           │ 自动同步公开手册
blog/docs/knowledge/ + blog/blog/ ─────────┼──→ blog-private 构建输入
                                           │
blog-private 内部内容 ──────────────────────┘

blog-private 内部原文
    ├── publication: internal-only ──→ 仅内部站
    └── publication: sanitized ──────→ 人工改写与审查
                                          ├── shine/docs/manual/
                                          └── blog/docs/knowledge/ 或 blog/blog/
```

同步只能沿箭头方向执行，不建立闭环。

### 8.2 `shine` 建议布局

```text
shine/
├── README.md                    # 简介、安装摘要、最短示例、文档入口
├── docs/
│   ├── manual/                  # 英文对外产品手册，默认 locale
│   │   ├── index.md
│   │   ├── installation.md
│   │   ├── quick-start.md
│   │   ├── guides/
│   │   ├── reference/
│   │   └── troubleshooting.md
│   ├── kb/                      # 内部开发知识，不进入公开构建
│   └── *-prd.md                 # 内部设计文档，不进入公开构建
└── website/
    ├── i18n/
    │   └── zh-Hans/             # 简体中文翻译内容根
    └── ...                      # 站点配置、主题与前端依赖
```

具体翻译目录可按最终站点工具调整，但英文源和 `zh-Hans` 翻译根必须显式配置。公开站构建不得以
“扫描整个 `docs/` 后逐项排除”的方式避免发布内部资料。白名单式内容根比排除规则更容易审计。

### 8.3 `blog` 迁移后布局

```text
blog/
├── docs/
│   ├── products/
│   │   ├── index.md
│   │   └── shine/               # 产品入口与旧 URL 兼容页，不是完整手册
│   └── knowledge/               # 公共通用知识
└── blog/                        # 公共博客
```

`blog` 的 Shine 产品入口应简要介绍产品并链接到独立站。旧手册路径应保留跳转或明确的迁移提示，
但不得复制新手册正文继续维护。

### 8.4 `blog-private` 聚合布局

逻辑上区分三类输入，实际目录名可在实施时根据 Docusaurus 约束确定：

```text
blog-private/
├── docs/
│   ├── products/shine/          # 从 shine 生成的公共手册副本
│   │   └── ...                  # 至少保留英文与简体中文两个 locale
│   ├── knowledge/               # 从 blog 生成的公共知识副本
│   ├── products/shine/internal/ # 本仓权威内部扩展
│   └── internal/                # 本仓权威内部通用指南
├── blog/
│   ├── ...                      # 从 blog 生成的公共文章
│   └── internal/                # 本仓权威内部时间流文章
└── .generated/
    ├── shine-manual-ref
    └── public-blog-ref
```

同步脚本必须先保护本仓内部目录，再更新生成内容。不得让 `rsync --delete` 的目标范围覆盖内部
权威目录。

内部站必须保持权威来源和发布边界严格分开，但阅读界面按任务融合。公共文章与本仓权威内部文章在
private 的 `/blog` 中按时间统一展示，并由主题层根据源路径标记“公开镜像”或“内部专属”；
`/internal/blog` 保留为内部文章筛选入口。内部文章仍只能存在于 `blog-private/blog/internal/`，不得
进入公共仓库、公共构建输入或任何 feed。

同一原则适用于文档导航：Shine 公开手册可与 Shine 内部扩展共用产品侧栏，公共知识可与内部实践
共用“知识与实践”侧栏。融合只发生在受访问控制的 private 阅读层，不改变内容权威来源或同步方向。

## 9. 公开站发布要求

### 9.1 发布分支

- 稳定公开站从 `shine/release` 发布。
- 功能分支和 PR 只执行构建、链接检查和必要的预览，不覆盖稳定站。
- `main` 或开发分支中的未发布命令不得默认出现在稳定文档中。
- 发布工作流应记录被部署的 commit SHA。

### 9.2 托管与域名

v1 使用 GitHub Pages 托管。实现必须支持项目 Pages 基础路径，例如：

```text
https://biulight.github.io/shine/
```

长期推荐使用独立自定义域名，例如：

```text
https://shine.biulight.top/
```

外部链接、README 和 Release 应优先使用自定义域名，使未来迁移到其他托管平台时无需修改所有
入口。域名尚未确定时，不阻塞先以 GitHub Pages 默认地址上线。

### 9.3 语言与本地化

- 公共站必须支持 `en` 和 `zh-Hans` 两个 locale。
- `en` 是默认 locale，访问站点根路径时展示英文，不进行基于浏览器语言的强制跳转。
- 简体中文使用稳定的 locale 前缀，例如 `/zh-Hans/`；最终路径一经发布不得随意改名。
- 导航栏必须在桌面端和移动端提供可发现的语言切换入口。
- 对应页面应共享稳定 doc ID，并尽可能在切换语言时停留在同一主题；目标语言没有对应页面时，
  不得静默跳到无关首页。
- 英文与简体中文覆盖相同的产品首页、安装、快速开始、指南、参考和排错页面集合。
- 两种语言描述同一版本和产品行为；代码与已发布命令仍是事实来源，英文不因默认 locale 身份而
  获得覆盖代码或中文已验证事实的更高权威。
- 用户可见功能变化必须在同一个发布 PR 中更新受影响的英文和简体中文页面。
- 可以使用机器翻译辅助起草，但稳定站发布前必须人工审阅术语、命令语义、链接和危险操作提示。
- 代码块、命令、配置键、路径、环境变量和官方产品名不做翻译；说明文字、标题、导航和可访问性
  文本需要本地化。
- 每种语言页面都应声明正确的 `lang`、canonical 和 alternate/hreflang，避免搜索引擎把翻译页
  识别为重复正文。

### 9.4 公开站内容

必须包含：

- 产品首页；
- 安装与平台要求；
- 快速开始；
- 面向任务的指南；
- 命令参考；
- 配置参考；
- 支持版本与兼容性说明；
- 故障排查；
- 返回 GitHub 仓库、Issue 和 Biulight 公共知识库的入口。

不得包含：

- `docs/kb/`；
- PRD、内部 ADR 和发布 Runbook；
- ShineOverlay 私有内容；
- 真实内部域名、地址、用户名、个人路径或私有仓库名；
- 任何凭据或可用于恢复凭据的信息。

以上页面集合必须同时具有英文和简体中文版本，不能用英文回退内容冒充已完成的中文支持。

### 9.5 README 收敛

Shine README 保留：

- 一句话定位；
- 支持平台；
- 最短安装方式；
- 最短成功示例；
- 完整手册链接；
- 贡献、Issue、安全与许可证入口。

完整命令表、配置字段和长篇任务流程迁入站点手册。默认 `README.md` 使用英文摘要；
`docs/README.zh-CN.md` 或后续等价中文入口可以保留简体中文摘要，但不再复制整套参考内容。
两个 README 应分别链接到对应语言的手册首页，并提供另一语言入口。

## 10. 内部站聚合与同步要求

### 10.1 双来源同步

现有 `blog-private/scripts/sync-public-content.sh` 从单一 `blog` 来源同步。迁移后必须支持：

1. 从 `shine` 的英文和简体中文公开手册内容根同步产品手册；
2. 从 `blog` 同步公共知识、公共博客和所需静态资源；private 可在展示层与受保护的
   `blog/internal/**` 合并，但不得把内部文件写回公共来源；
3. 不从 `blog` 同步旧的 Shine 兼容页覆盖产品手册；
4. 不删除或覆盖 `blog-private` 的内部权威目录；
5. 分别记录两个源仓库的 commit SHA；
6. 任一来源缺失、目录错误或同步失败时立即失败，不发布部分更新的站点。

默认相邻检出可使用：

```text
SHINE_REPO_DIR=../shine
PUBLIC_BLOG_DIR=../blog
```

CI 中可以覆盖路径，但必须解析并校验为预期仓库，不能静默退回陈旧副本。

### 10.2 生成内容保护

同步生成的公共副本必须满足至少一种保护方式：

- 文件头包含“Generated, do not edit”标记；
- 路径由仓库规则声明为生成目录；
- CI 在同步后执行 `git diff --exit-code` 或等价检查，发现人工修改即失败；
- AGENTS 指令明确要求只能修改源仓库。

生成副本是否提交到 `blog-private` 可在实施时选择，但必须满足：

- 构建可复现；
- 来源 revision 可追溯；
- 两个 locale 来自同一个 Shine revision；
- 不依赖维护者未声明的本机状态；
- 不会因某个公开源暂时不可用而错误发布半新半旧内容。

### 10.3 内部站访问控制

- 内部站继续使用 VPN、内网或认证控制访问。
- `robots.txt`、`noIndex` 和关闭 sitemap 只能作为辅助防索引措施，不是安全控制。
- 内部站构建产物不得上传为公开 GitHub Actions artifact 或部署到公开 Pages。
- CI 日志不得打印内部文档全文、敏感配置值或完整拓扑。
- 截图和附件同样受公私分类规则约束，并需检查可见标识和元数据。

## 11. 内部内容的公开衍生流程

### 11.1 Front Matter

内部原始页面继续使用：

```yaml
publication: internal-only
```

可脱敏发布的页面使用：

```yaml
publication: sanitized
public_repository: shine
public_target: docs/manual/guides/example.md
```

或：

```yaml
publication: sanitized
public_repository: blog
public_target: docs/knowledge/example.md
```

`public_repository` 仅允许 `shine` 或 `blog`。`publication: sanitized` 时，
`public_repository` 和 `public_target` 都是必填字段。

### 11.2 目标仓库选择

- 公开版本主要解释 Shine 独有行为或任务：选择 `shine`。
- 公开版本可以脱离 Shine 独立成立：选择 `blog`。
- 脱敏后会失去关键操作价值，或仍暴露内部结构：改为 `internal-only`。

### 11.3 脱敏审查

发布公开衍生版本前必须人工检查并替换或删除：

- 真实域名、IP、主机名、用户名和账户标识；
- 个人绝对路径、共享目录和挂载位置；
- 私有仓库、内部组织和内部任务名；
- 网络拓扑、端口暴露和访问控制细节；
- 截图、附件、图片元数据和终端提示符中的内部标识；
- Token、密码、私钥、Cookie、恢复码及其可逆编码；
- 即使不属于凭据，也足以帮助外部推断内部资产的信息组合。

公开版本必须为面向公共读者的重新组织与改写，不能通过批量替换生成。公开版本不得反向覆盖
内部原文。

## 12. URL、链接与搜索迁移

### 12.1 旧 URL 兼容

当前 `/products/shine/**` 页面不能直接删除。迁移时建立旧路径到新站点对应页面的映射表：

| 旧路径类型 | 处理方式 |
|---|---|
| Shine 首页 | 永久跳转或保留门户页并提供明确入口 |
| 安装、快速开始、参考页 | 跳转到新站对应页面 |
| 已合并或改名页面 | 跳转到最接近的新目标，不跳到无关首页 |
| 无对应内容 | 保留说明页并给出新的导航入口 |

若当前托管层支持 HTTP 301/308，优先使用服务端永久跳转；纯静态 Pages 无法提供真实状态码时，
使用 Docusaurus client redirect 或轻量兼容页，并设置 canonical 指向新 URL。

当前 `blog` 中的 Shine 手册以简体中文为主，因此旧 `/products/shine/**` 路径必须跳转到新站的
`zh-Hans` 对应页面，不能因为新站默认语言是英文而统一跳到英文根路径。

### 12.2 跨站链接

- Shine 手册引用通用知识时使用公共绝对 URL，不依赖 `blog` 的相对目录结构。
- `blog` 的产品入口和知识文章使用 Shine 文档的稳定域名。
- 站内链接应保留当前 locale；语言切换器负责在英文与简体中文对应页之间切换。
- 内部站同步阶段可按需重写公共绝对链接为内部镜像路径，但源文件中仍保存公共稳定 URL。
- 链接重写必须是显式规则，不得对所有 URL 做无差别字符串替换。

### 12.3 搜索与索引

- 新 Shine 站点必须索引英文和简体中文正文，并根据当前 locale 优先展示同语言结果；具体搜索
  实现不作为 v1 硬性技术选型。
- 新站上线后更新公共搜索索引范围，并停止索引旧手册正文。
- 旧页面使用 canonical 或跳转，避免搜索结果中出现两套同内容页面。
- `blog-private` 使用独立的本地或内部搜索索引，不向公共搜索服务上传内部正文。

## 13. CI 与质量要求

### 13.1 `shine` 仓库

涉及公开手册或站点代码的 PR 至少执行：

- 安装锁定版本的站点依赖；
- 构建公开站；
- 分别构建或验证英文与简体中文 locale；
- 检查两个 locale 的 doc ID、页面集合、导航目标和静态资源完整性；
- 检查受影响的用户可见功能没有只更新单一语言；
- 检查内部链接和静态资源；
- 检查公开内容根没有包含 `docs/kb/`、PRD 或其它非手册目录；
- 对命令和选项执行现有文档验证流程，必要时对照 `--help`；
- 检查示例不包含真实凭据和私有环境标识；
- `git diff --check`。

站点或导航使用 TypeScript 时还需运行对应 typecheck。

### 13.2 `blog` 仓库

迁移期间及迁移后至少执行：

- `pnpm build`；
- React、TypeScript、导航或主题变化时运行 `pnpm typecheck`；
- 检查旧 URL 兼容页与跨站链接；
- 检查不再存在可编辑的 Shine 手册副本；
- `git diff --check` 和 `git status --short`。

### 13.3 `blog-private` 仓库

至少执行：

- 双来源公共内容同步；
- 校验两个来源 revision；
- 检测生成内容被人工修改；
- `pnpm build`；
- `pnpm typecheck`；
- 检查公共衍生版本的目标元数据；
- 检查内部内容未进入公共目标目录或公开构建流程；
- `git diff --check` 和 `git status --short`。

## 14. 迁移计划

### 阶段 0：冻结边界与建立清单

1. 盘点 `blog/docs/products/shine/` 的所有页面、资源、入口和外链。
2. 将现有简体中文页面标记为 `zh-Hans` 迁移源，并为每页建立英文对应页清单。
3. 标记每页的英文、简体中文目标路径及是否需要重写。
4. 盘点 README 与中文 README 中和手册重复的内容。
5. 盘点 `blog-private` 的同步输入、内部保留目录和 public target。
6. 建立旧中文 URL 到新 `zh-Hans` URL 的完整映射表。

完成标准：每个现有页面和资源都有唯一处理结论，没有“稍后决定”的未分类文件。

### 阶段 1：在 `shine` 建立公开站

1. 建立英文默认内容根、`zh-Hans` 翻译根和站点构建外壳。
2. 把现有手册迁入简体中文 locale，并创建经过审阅的完整英文版本。
3. 对齐两个 locale 的 doc ID、页面集合、导航顺序和静态资源。
4. 修复两种语言的站内链接与跨站链接。
5. 限定构建只读取两个显式公开内容根。
6. 增加双 locale 构建、页面对齐、链接和类型检查。
7. 收敛 README，分别指向英文和简体中文手册，但暂不删除旧站内容。

完成标准：本地和 CI 构建通过；英文和简体中文都覆盖现有手册全部用户任务；语言切换保持对应
页面；内部文档未进入构建产物。

### 阶段 2：GitHub Pages 上线

1. 配置 `release` 分支发布工作流。
2. 使用默认 Pages 地址验证英文根路径和 `zh-Hans` locale 路径。
3. 配置自定义域名时，同时验证 TLS、canonical、基础路径和静态资源。
4. 更新 GitHub About、README、Release 模板和 Issue 入口。

完成标准：稳定 URL 可访问，部署 revision 可追溯，非 `release` 分支不会覆盖稳定站。

### 阶段 3：调整 `blog` 门户与旧链接

1. 将 Shine 产品首页改为独立站入口。
2. 为旧中文手册路径建立到新 `zh-Hans` 对应页的逐页跳转或兼容页。
3. 保留跨产品公共知识，不迁入 Shine。
4. 更新首页、产品索引、导航和搜索配置。
5. 删除旧手册的可编辑正文，防止形成第二权威源。

完成标准：所有旧 URL 都有合理目标；`blog` 构建无坏链；搜索结果不会长期保留两套正文。

### 阶段 4：升级 `blog-private` 聚合

1. 将同步脚本改为 `shine` 与 `blog` 双来源，并同步 Shine 的两个 locale。
2. 保护内部权威目录不受删除同步影响。
3. 分别记录 `shine-manual-ref` 和 `public-blog-ref`。
4. 为生成副本增加禁止编辑检查。
5. 为 `publication: sanitized` 增加 `public_repository` 校验。
6. 验证内部导航、搜索和所有内部专属页面。

完成标准：内部站同时包含最新公开手册、公共知识与内部扩展；任一源缺失时同步安全失败；内部内容
不会出现在公开构建中。

### 阶段 5：清理旧流程

1. 从 `blog/.agents/projects.yml` 移除 Shine 手册的跨仓审阅职责，或改为仅记录门户链接兼容状态。
2. 在 `blog-private/.agents/projects.yml` 中分别记录公开手册、公共博客和 ShineOverlay 来源。
3. 更新三个仓库的 AGENTS 指令和维护文档。
4. 删除不再使用的单来源同步参数与脚本逻辑。
5. 观察旧 URL、搜索和内部同步至少一个发布周期后再清理临时兼容措施。

完成标准：维护者根据任一页面路径都能唯一判断权威仓库和验证命令。

## 15. 验收标准

### 15.1 内容一致性

- [ ] Shine 每篇公开产品手册的英文和简体中文版本都只在 `shine` 中维护。
- [ ] Shine 用户可见变更的贡献说明要求同步更新相关手册。
- [ ] 稳定站内容对应 `release` 分支，部署 revision 可查询。
- [ ] `en` 是默认 locale，`zh-Hans` 路径稳定且两种语言页面集合一致。
- [ ] 语言切换能到达同一主题，两种语言均无未审阅的机器翻译或英文占位回退。
- [ ] README 不再复制完整命令与配置参考。
- [ ] 通用知识仍由 `blog` 维护，并可从 Shine 手册访问。

### 15.2 公私边界

- [ ] 公开站构建只读取显式的公共手册内容根。
- [ ] `blog-private` 内容没有进入 `shine` 或 `blog` 的 Git 历史和构建产物。
- [ ] 内部站依赖真实访问控制，而非仅依赖 `noIndex` 或隐藏 URL。
- [ ] `publication: internal-only` 页面没有公开目标。
- [ ] `publication: sanitized` 页面具有合法的目标仓库和路径，并经过人工脱敏审查。

### 15.3 同步可靠性

- [ ] `blog-private` 能从 `shine` 和 `blog` 分别同步所需公共内容。
- [ ] `blog-private` 同步的 Shine 英文与简体中文手册来自同一个 commit。
- [ ] 两个源 commit SHA 被分别记录。
- [ ] 缺失任一输入时同步失败且不会发布部分更新。
- [ ] 内部权威目录不会被 `--delete` 或其它清理操作覆盖。
- [ ] 人工编辑生成副本时 CI 会失败并指向正确源仓库。

### 15.4 迁移体验

- [ ] 现有 `/products/shine/**` URL 均有跳转、canonical 或明确兼容页。
- [ ] README、GitHub About、Release 和公共产品入口使用稳定新域名。
- [ ] 新旧站均无坏链和丢失静态资源。
- [ ] 公共搜索停止把旧正文作为独立结果持续索引。
- [ ] 内部站导航和搜索可以同时找到公开手册与内部扩展。

## 16. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 三个站点增加维护成本 | 依赖、主题、搜索配置漂移 | 只要求信息架构一致，不强求技术栈完全一致；锁定依赖并由 CI 验证 |
| 迁移后产生重复正文 | 用户和搜索无法判断最新版 | 删除旧权威副本，使用跳转与 canonical，建立 URL 映射表 |
| 内部同步误删私有内容 | 内部知识丢失 | 分离生成目录与权威目录；同步前校验目标；禁止扩大 `--delete` 范围 |
| 内部内容泄露到公开站 | 安全事故 | 公开构建采用内容根白名单；对构建产物执行路径与关键词审计 |
| 文档发布早于功能发布 | 用户看到尚不可用命令 | 稳定站只从 `release` 发布；PR 预览不替换稳定站 |
| 两种语言内容漂移 | 不同用户得到不同命令或安全提示 | CI 检查页面集合；用户可见变更同 PR 更新两种语言并人工审阅 |
| 脱敏流程被误当作自动转换 | 残留内部标识 | 强制人工改写、目标元数据和审查清单，不提供通用自动发布命令 |
| GitHub Pages URL 被长期绑定 | 后续迁移困难 | 对外使用自定义域名；Pages 仅作为托管实现 |
| 跨站链接在内部镜像中跳出 | 内部体验割裂 | 对少量已知公共域名做显式内部链接重写，同时保留源文件公共 URL |

## 17. 回滚策略

迁移按阶段执行，任何阶段均不得通过恢复双写来回滚。

- 新站未上线：继续使用 `blog` 现有手册，`shine` 站点作为未发布预览。
- 新站已上线但入口未切换：修复新站后再继续，旧站保持权威。
- 入口已切换但新站故障：临时把产品入口指向最后一次可用构建，不恢复两份人工维护正文。
- 内部双来源同步故障：停止内部站发布，使用最后一次已验证构建；不得发布部分同步结果。
- 发现私有内容泄露：立即停止公开部署、撤下产物并轮换可能暴露的凭据；仅删除页面不足以清除
  Git 历史和缓存，必须按安全事件流程处理。

只有在 `blog` 的旧正文尚未删除前，才允许将公开入口整体切回旧站。旧正文删除后，回滚单位应是
新站的已知良好构建，而不是重新建立双权威来源。

## 18. 实施前待确认事项

以下事项不改变本 PRD 的内容边界，可以在实施 PR 中决定：

1. Shine 公开站继续使用 Docusaurus，还是采用更轻量的静态文档工具；
2. 最终自定义域名使用 `shine.biulight.top`、`docs.shine.biulight.top` 或其它名称；
3. `blog-private` 的公共生成副本提交到 Git，还是仅在可复现构建阶段生成；
4. 旧 URL 使用托管层永久跳转、Docusaurus redirect 插件，还是静态兼容页；
5. 公共站搜索继续使用现有 Algolia 索引，还是建立 Shine 独立索引；
6. 是否在后续版本增加“当前稳定版 / 下一版本”双通道文档。

这些选择必须满足本 PRD 的唯一权威源、安全边界、稳定版发布和可追溯同步要求。

## 19. 核心决策摘要

- Shine 英文和简体中文公开手册迁入 `shine`，与产品版本共享提交和发布边界。
- 公共站默认语言为英文，简体中文使用稳定的 `zh-Hans` locale 路径，两种语言覆盖相同页面集合。
- `blog` 保留 Biulight 门户、博客和跨产品知识，不再维护 Shine 完整手册副本。
- `blog-private` 保留全部内部权威内容，并聚合两个公开来源供内部阅读。
- 公开内容流向内部站使用自动单向同步；内部内容流向公开站必须人工脱敏改写。
- 每篇内容只有一个可编辑权威来源，不允许双写或双向同步。
- 公开站只从显式手册内容根构建，任何隐藏或排除机制都不能替代访问控制。
- 稳定文档从 `shine/release` 发布；GitHub Pages 是首选托管实现，自定义域名是长期公共入口。
